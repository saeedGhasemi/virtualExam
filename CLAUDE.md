# MetaQuizy — notes for Claude

Online exam system (Persian UI, RTL). Roles: student, teacher, academic_manager, admin.
**Reply to the user in Persian.** Session progress lives in `PROGRESS.md`; how to run and deploy is in `README.md`.

## Session workflow (the user opens a new chat per task)
- Start: read `PROGRESS.md` (short). Read only the code the task needs.
- Several chats may work in the same tree: run `git status` first, never revert or overwrite changes you didn't make, and re-read `PROGRESS.md` right before editing it.
- End of every chat that changed something: update `PROGRESS.md` (what changed, tested or not, committed or not, deploy impact such as migrations or new static files). Add to `CLAUDE.md` only lasting rules/conventions; to `README.md` only run/deploy procedure changes. Keep all three short, no duplication, no secrets.

## Stack
- Django 5.1.9, PostgreSQL (psycopg 3), WhiteNoise, gunicorn; openpyxl, Pillow, pyotp, qrcode (`requirements.txt`).
- One app: `apps/core`. Settings: `config/settings.py` (reads `.env`; `DB_ENGINE=postgres` locally).
- Frontend: Django templates in `templates/<role>/`, Bootstrap 5 + jQuery, Tailwind build (`npm run build:css`), custom CSS in `static/css/`.
- `TIME_ZONE='Asia/Tehran'`, `USE_TZ=True`, `LANGUAGE_CODE='fa-ir'`.

## Code conventions
- Most data access is raw SQL through `erd_rows` / `erd_row` / `erd_execute` / `erd_has_column` (`apps/core/views.py` ~line 625), not the ORM. Tables are ERD tables (`profiles`, `exams`, `exam_attempts`, `questions`, …); Django models are mostly legacy.
- `apps/core/views.py` is ~18.5k lines and **some functions are defined more than once — only the last definition is live.** Grep for `^def name` and edit the last one. Never read the whole file.
- Other modules: `teacher_preferences.py`, `grading_views.py`, `exam_schedule.py`, `student_dashboard.py`, `student_settings.py`, `teacher_question_bank.py`, `teacher_students.py`, `osce_views.py`.
- «پیش‌نمایش» of any exam/question is `exam_preview.py` on the real `student/attempt.html` (students get sample questions, nothing is saved). Link new exam/question pages to `core:exam_preview` / `core:question_preview` with `?new=1`; a change to the attempt page must keep its `preview` branches working. The attempt page switches questions without a reload (form contents swapped; `.qx-pos` / `.qx-dock` swapped or updated in place): code for elements inside them goes in `initQuestionArea()` (set-up per block runs once: a revisited question gets its own nodes back) or uses delegation. When going back is allowed and answers may change, it fetches every question once (`?part=questions`, `views._sx_render_attempt_page`, 404 in other modes) and moves offline-capable without the network, so a GET of the attempt / preview page must change nothing on the server in that mode. Answers go through a device-side outbox (localStorage, retried until the server confirms, recovered when the attempt reopens): header comments «Saving» / «Recovery» / «Moving between questions» in `attempt.html`.
- Timestamp columns without time zone store UTC (see `_db_naive_datetime`). Display dates in Jalali via `templatetags/core_extras.py`.
- Exam settings columns carry defaults for every exam; what applies is `_sx_exam_rules(exam_id)` (wizard values only when `settings_enforced`). Read effective settings from it, not from the raw columns.
- A global JS converter in `base.html` / `base_standalone.html` turns digits Persian (as does `|fa_digits`), except inside Latin words (`MQTEST-T02`, e-mails); numeric codes/IDs (personnel code, student number, national ID, course code) are shown with `data-latin-digits` and without `|fa_digits` (user's choice; editors are excluded).
- System appearance (admin «تنظیمات ظاهری», `apps/core/appearance.py`): `static/js/appearance.js` recolours brand blues at runtime, so hardcoded blues are fine; inline colours that must stay as written go inside `data-mq-keep`. Any new page with its own `<html>` needs the `data-mq-*` attributes + `{% include "partials/appearance_head.html" %}` before `</head>`. That partial also holds the anti-flash load gate (font preload, `font-display:block`, body hidden until parsed) — don't re-add `@font-face`/`swap` elsewhere. Every account also has its own «تنظیمات ظاهری» with the admin's options, preview + «ذخیره تغییرات» (`partials/my_appearance.html`, stored as `user_appearance.<profile id>`): read the effective values from `mq_appearance`, the admin's from `mq_system_appearance`.
- Filters, search, paging, calendar navigation **and same-page tabs** must not reload the page: wrap filter form + results (for tabs: tabs + tab content, nested regions allowed; `data-live-region="contents"` = no layout box) in `id="…" data-live-region` (`static/js/live-region.js`; header comment has the details). Auto-submit with `this.form.requestSubmit()`, never `form.submit()`. Text search is never sent while typing — only on Enter / the search button (user's requirement; selects/checkboxes may auto-submit). JS bound to elements inside a region must use delegation, rebind on `mq:live-load`, or sit inside a `data-live-scripts` region (inline scripts re-run; no document listeners there); mark download/reset links `data-live-skip`.
- Listing tables are handled by `static/js/responsive-tables.js` (header comment): every column, header and cells alike, centred (user's choice); wrap-to-fit, else a card grid; a table/card switch is `{% include "partials/rt_view_switch.html" with key="…" %}` (opens as a table — user's choice: lists of exams, questions, users default to rows; `default="cards"` only for summary tiles such as question banks). In table view every listing table gets one compact look (model: teacher dashboard «آزمون‌های پیش رو»: small grey head, short rows, normal-weight cells, small pills, 2rem icon buttons) from the end of `responsive.css`; don't restyle th/td sizes per page. Don't add per-page centring or horizontal scrolling for tables; opt out with `rt-off` / `data-rt-align="keep"`. Action-column buttons with a known label become icon buttons automatically (`ICONS` in that file; keep a button as text with `data-rt-text`).
- Rows/cards open their item from anywhere, not only the name (user's choice): `static/js/row-link.js` (header comment) does it for listing table rows automatically (title-cell link, else the row's only link); give other cards/rows `data-row-href="url"`, opt out with `data-row-link="off"`.
- Lists show at most 10 items per page (user's choice): `static/js/list-pager.js` (header comment) pages every listing table client-side (and any container marked `data-pager`, e.g. a card grid), no reload; server-paged lists use page size 10 so they never get a second pager and render their pager with `{% mq_pager page_obj %}` (same look, nothing at one page; JS-paged lists: `window.mqPager.markup()`); no per-page («تعداد نمایش») picker anywhere (user's choice). Don't add fake/static pager markup.
- No layout jumps (user's requirement): JS that restyles content must finish before the first paint of it — on `DOMContentLoaded` / synchronously in `mq:live-load` / `mq:pager` handlers, never after a `setTimeout`/debounce — and must batch DOM reads before writes (a read after each write forced ~0.9s of relayout in `responsive-tables.js`).
- Font weights (user's choice, not too bold): body 400, labels/buttons/nav/badges 600, titles and numbers 700; never 800 or more (`tailwind.config.js` makes `font-black/extrabold/bold` 700/600/600; Tailwind source `static/src/input.css` → `npm run build:css`, or `node node_modules/tailwindcss/lib/cli.js …` when the script isn't on PATH).
- Text size (user's choice, compact): the root size comes from `static/css/appearance.css` («متوسط» = 14.5px, «کوچک» = 13px); size text in rem so it follows. px font sizes are scaled at runtime by `appearance.js` (`--mq-fs`).
- Wrapping strips (tabs, steps, type pickers) are flex-wrap rows with growing items, balanced by `static/js/balanced-rows.js` (add `data-balance-rows`); never `repeat(auto-fill,…)` for them (leaves empty columns). Card grids use `repeat(auto-fit,…)` so a few cards stretch to fill the row (no empty columns, user's choice); `auto-fill` only where fixed-size tiles are intended (e.g. question map).
- Cards side by side (user's choice): same height and aligned (grid `stretch`, never `align-items:start` for a card row), but the row is only as tall as its tallest content — no fixed `min-height`, no `flex-grow`/`100dvh`/JS to stretch content to the window (pages end just after their content); empty-state text sits centred in the card.
- Date/time fields use `static/js/jalali-datepicker.js` (header comment): limits with `data-jalali-min="now"` / `data-jalali-max-days` / `root.mqJalaliBounds`; an exam's times are checked by `views.exam_timing_problem` (wizard + exam hub) with a browser twin in `exam_wizard.html` — change both.
- Every page must work down to **240px** wide (user's requirement; audit with Playwright at 240/320/390/768/1024/1440). Single-column grids use `grid-template-columns:minmax(0,1fr)` (a bare grid or `1fr` grows to its widest child and cuts the page). Page `<style>` blocks load after `responsive.css`, so overrides there need a doubled class (`.a.a`) or `!important`.
- Keep the existing structure and templates; don't create new templates/patterns where an existing one fits.
- When you change a static JS/CSS file, bump the `?v=` on its `{% static %}` include (locally `DEBUG=True` serves unhashed URLs without Cache-Control, so browsers keep the old file).
- Release number: the root `VERSION` file (Semantic Versioning `MAJOR.MINOR.PATCH`, started at `1.1.0` at the teacher's request) is shown as `v…` under every logo (`settings.APP_VERSION` → `app_version` context → `partials/brand_logo.html`). Bump it in the commit of every deploy: PATCH for fixes, MINOR for new features, MAJOR only for a big incompatible change; record the version next to the commit in `PROGRESS.md`.
- Schema changes go in a new migration in `apps/core/migrations/` (latest: `0066`).
- One device per account, every role (user's choice): a sign-in ends the account's other sessions (`account_security.end_replaced_sessions`; the signed-out device is told why). Tests needing two live sessions of one user can't just log in twice.
- Sessions are DB-backed (`config/settings.py`): the cache is per process, so never store session data through it. A value several overlapping requests change (e.g. preview state) is written under `exam_preview._session_locked`.
- Scheduled DB backups: `apps/core/auto_backup.py` (header comment) — an in-process scheduler thread per web process + pg advisory lock; anything that replaces or dumps the whole DB takes `auto_backup.exclusive()`.
- Access levels are fixed (`apps/core/org_levels.py`, user's teacher's model): 1 مدیر سیستم › 2 دانشگاه › 3 بخش (its academic manager) › teachers; levels 2–3 are `academic_manager` scoped to a university / department. Use `org_levels.request_level()` / `can_manage_structure()` for level checks, never editable levels.
- Deleting a course or a student/teacher/manager account goes through `apps/core/deletion.py` (dialog: item only / with all records; code: `delete_account`, which also removes the login — a leftover `auth_user` was reused by a new account with the same e-mail); don't hand-write `DELETE FROM courses|profiles` elsewhere.
- Exam lists (teacher «آزمون‌های من», manager/admin «آزمون‌ها») share one component from the user's mock-up: `apps/core/exam_list.py` + `templates/partials/exam_list/` + `css/exam-list.css` / `js/exam-list.js` (header comments); change it there, not per page.
- Per-exam management (overview, live monitor, grading queue, results/analysis, events, review, settings) is one page: `apps/core/exam_hub.py` + `templates/exam_hub/` (header comment); exam-list buttons for scheduled/running/finished exams lead there. An attempt's end always goes through `_sx_attempt_ends_at(…, extra_minutes)` (`_sx_attempt_deadline`; server accepts answers `ATTEMPT_GRACE_SECONDS` = 30 after it); closing an attempt (submit / expire) goes through `views._sx_claim_attempt_close` (atomic, submitted_at never after the deadline), never a bare `UPDATE … submitted_at`. Expired attempts are closed by `exam_schedule.py`'s per-process thread (`DUE_TASKS_SCHEDULER`, header comment); the attempt page's clock follows the server both ways (live check-in).
- A teacher's class page (overview, students + «عملکرد دانشجو», class exams) is `apps/core/teacher_class.py` + `templates/teacher/class/` + `css/class-hub.css` (header comment); it reuses the exam hub's `.xh` styles and the exam list's actions.
- All four dashboards share one look and layout (model: teacher dashboard, user's choice) but each keeps its own content: `templates/partials/dashboard/` (styles + parts); change the look there so they stay identical, never add/remove a dashboard's content to make them match.
- Question-type filters are a multi-select dropdown, never tiles (user's choice): `{% include "partials/type_multiselect.html" %}` + `css/type-multiselect.css` / `js/type-multiselect.js` (header comments).
- An open course exam locks the session to it (`apps/core/exam_lock.py`: other page loads redirect to the attempt; the attempt page traps Back and asks before leaving). Code on the attempt page that navigates on purpose calls `allowLeave()` / `window.mqAllowLeave?.()` first; new attempt sub-URLs stay under `/student/attempts/<id>/`.
- Loading: `static/js/page-loader.js` (header comment) shows the logo loader automatically from the user's action until the result is on screen (user's choice: everywhere, on at the click, off when loaded, never on its own) — page loads, Back/refresh, live regions, user-started `fetch()`/XHR; background requests (autosave, polling) must pass `{mqBackground: true}`; opt an element out with `data-no-loader`; manual: `mqLoader.start()/stop(id)/track(promise)`. Don't add per-page spinners/overlays.
- Forms whose save/apply button should stay disabled until something changes: `data-dirty-form` on the form, `data-dirty-submit` on the button, `data-dirty-reset` on «بازنشانی»/«پاکسازی» (`static/js/dirty-form.js`); the server still saves and reports only real changes («تغییری ثبت نشد» otherwise). «؟»/«i» help icons are `<button type="button" data-help-tip="…">` (`static/js/help-tip.js`), never `title=` alone. File inputs use `partials/file_picker.html` (Persian picker), not the bare browser control.
- Old browsers without CSS `:has()` are handled by `static/js/has-fallback.js` (rewrites `:has` rules; keep `:has` selectors simple: compound + relative argument). A refused page opened in a browser shows `templates/403.html` (`middleware.ForbiddenPageMiddleware`).
- Messages and confirmations: Django `messages` show as the shared top toast (`partials/flash_messages.html`); ask with `window.mqConfirm()` / `data-confirm` (`partials/confirm_dialog.html`), never the browser's `confirm()`.
- Form fields side by side line up (user's requirement): a label/field wrapper that is a grid or column flex gets `align-content:start` (never stretch), and a required star inside it is `<em class="mq-req">*</em>` (or `.req`), which `responsive.css` turns into `display:contents` so it stays on the label's line.
- Personal-data inputs (national ID, mobile, landline, Jalali dates, email, names, student/personnel code, username, entry year) get format rules + example placeholders (bare example, no «مثلاً» — user's choice) automatically from `static/js/field-rules.js` (by name/type; header comment; wrong keys are refused as typed with a hint under the field); it also covers every `type=number` box (digits only, Persian min/max messages, example placeholder from `NUM_PH`) and codes / academic year / 2FA code / colour / IP range, and every password box (English letters, digits, symbols only; new-password meets the password standard — ≥ 8 with upper + lower English letter, digit and symbol, what is missing is named in the message under the box; no static rule hints and no checklist chips (user's choice) — repeat must match; server twins `field_rules.LatinPasswordValidator` / `PasswordStrengthValidator` (`PASSWORD_RULES`), generated passwords via `account_security.generate_temporary_password`). Field messages are solid boxed notes (`.mq-rule-msg`, `.auth-field-error`). Server-side twin `apps/core/field_rules.py` (`format_error` refuses a wrong-format personal field on every signed-in POST via `PersonFieldLengthMiddleware`, except pages in its `SELF_VALIDATING` that show the error on their form). New text boxes need an example placeholder. Never pre-fill such fields with fake sample values; leave them empty. Rules are realistic, like professional sign-up forms (user's requirement, header of `field_rules.py` / `field-rules.js`, keep both in step): names ≤ 30/40 letters, one script, word ≤ 20; e-mail ≤ 100 (local ≤ 64); username 3–30 or an e-mail; codes 3–20; student number 4–15 digits; mobile 090–094/099; birth date age 15–100. Every `birth`/`date` box gets a Jalali calendar button automatically (`static/js/date-field-picker.js`, loaded before `field-rules.js`).
- Length caps for personal / basic-info fields: `field_rules.FIELD_MAX` (by POST name), enforced for every signed-in POST by `middleware.PersonFieldLengthMiddleware` and mirrored as `maxlength` by `field-rules.js`; a new such field name goes in both. A wrong-format value already stored unchanged passes (`_STORED_IN`); Excel imports check rows with `field_rules.record_issues`. Record titles / names / codes / numbers: `field_rules.TEXT_RULES` (length + longest unbroken word) and `NUMBER_RANGE`, mirrored in `field-rules.js` (`TEXT_RULES` / `NUM_RANGE`); a new record field name goes in both; leave out names a view validates itself with an on-form message.
- Passwords are never displayable (hashes only): show `••••••••` + last change, offer a change/reset form. Any code that sets a password calls `account_security.mark_password_set(user, change_required=…)`.
- Security docs: `Security.md` (secrets/.env, hashing), `Auth.md` (login, `auth_events`, throttle), `Data.md` (personal data, retention, `purge_expired_data`), `Hack.md` (attacks/defences). Every new view needs a role decorator (`student_required` / `teacher_required` / `exam_manager_required` / `super_admin_required` / `erd_role_required`): `apps/core/tests_security.py` sweeps all routes anonymously and as student/teacher. All sign-ins go through `SecureLoginView` (throttle in `auth_guard.py`); client IP only via `client_ip()`. No secret in code; demo passwords only behind `DEBUG`.

## Production (https://metaquizy.ir) — precautions
- Ubuntu server, systemd `metaquizy.service` (gunicorn on 127.0.0.1:8020), app at `/srv/sites/metaquizy/app`. No sudo for us.
- **Install nothing and move nothing on the server; ship code only.** Don't delete pre-existing data.
- **"Deploy the latest version" / «آخرین نسخه رو ببر روی سرور»** means: follow `README.md` → «ارسال آخرین نسخه به سرور» steps 0–6 yourself, then stop and hand the user the one `sudo bash …/apply-update.sh` line for the teacher. Summary:
  1. Tests green; ask the user before committing uncommitted work; server's current commit (`OLD`) is in `PROGRESS.md`.
  2. Package `git diff OLD..HEAD` files with `git archive` (+ `deleted.txt`), `scp` to a new `~/metaquizy-backup-<timestamp>/`.
  3. On the server: `files-before.tar` + `pg_dump` backup; verify in `~/mq-verify` with the server venv (`check`, `migrate --plan`); write `apply-update.sh` + `rollback.sh` (templates in README; set the rollback migration target if the package has migrations).
  4. After the teacher runs it: verify (service active, `127.0.0.1:8020` 200, deployed files match), then update `PROGRESS.md` with the new server commit.
- **Full deploy by us («ببر روی سرور و دامنه»):** if the user also gives the **root** SSH login, do steps 0–5 with the normal user, then run `bash ~amirhossein/metaquizy-backup-<ts>/apply-update.sh` over `ssh root@…` yourself (root needs no `sudo`) and do step 4's verification — including public `https://metaquizy.ir/login/` 200 and that it serves `css/responsive…`. Before applying, confirm `files-before.tar` still matches the live files. If root isn't given, stop and hand over the one-line command. The script's `site check: 301` is the http→https redirect, not an error (add `-H 'X-Forwarded-Proto: https'` to get 200).
- **What the user gives for a deploy:** normal SSH `user@host` + password, DB name + DB user + DB password (for `pg_dump`), and optionally root `user@host` + password (to apply it ourselves). Server path is fixed (`/srv/sites/metaquizy/app`). Uncommitted work is not shipped — ask before committing it, never include another chat's unfinished work without asking.
- **Credentials:** the user types SSH/DB credentials into the chat each time. Use them only for that run (e.g. a temporary `SSH_ASKPASS` script in the scratchpad, `PGPASSWORD` inline), delete helper files afterwards, and never write them into any repo file, commit or memory.
- The server can't reach its own domain (curl returns 000); health-check `127.0.0.1:8020` instead.
- `DEPLOY.md`, `RAILWAY.md`, `render.yaml`, `railway.json` and `deploy/` describe other hosting targets, not the current server.
- Never write passwords or keys into repo files.
